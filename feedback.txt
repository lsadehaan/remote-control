## Critical gaps / high-risk areas (fix these early)

### 1) Docker socket = host root-by-proxy

If your backend can talk to `/var/run/docker.sock`, compromise of the backend or a bug in your “terminal bridge” can become **host compromise** (create privileged containers, mount host FS, etc.). This is the #1 real-world failure mode for platforms like this. Docker themselves explicitly warn that broad access to the Docker socket reduces security. ([Docker Documentation][1])

**Mitigations (pick at least two):**

* Run the backend with **least privilege** and lock down *what* it can ask Docker to do:

  * Allowlist images/templates (no arbitrary image name).
  * Disallow privileged, host networking, host PID, docker socket mounts, device mounts.
  * Force a fixed mount: only the project volume → `/workspace`.
* Consider **rootless Docker** (or a separate Docker host/VM) if you want stronger isolation.
* Put the “Docker API” behind a narrow internal service that only exposes “start/stop/exec/logs” for known containers, not arbitrary container creation.

### 2) File browser must be “jail-safe”

A WebSocket file browser is a path traversal / symlink-escape magnet.

**Requirements:**

* Canonicalize paths (realpath) and enforce: `realpath(requested).startsWith(realpath(workspaceRoot))`.
* Decide explicitly what you support:

  * Read-only browsing? file download? editing? (Editing multiplies risk.)
* Prevent “zip-slip” equivalents (archives) if you add download/upload later.

### 3) Credential flow as described is ambiguous and risky

> “Temp container for auth → extract credentials → store in Vault → destroy container”

This can be safe, but you need to define:

* **What is the credential artifact?** (API key? OAuth refresh token? local CLI config file?)
* **Where is it stored in the temp container?** (home dir? keychain emulation? plaintext file?)
* **How do you extract it without logging or leaking it to the websocket terminal?**

**Safer patterns:**

* Prefer “user supplies token/key directly” into a secure UI form → store in Vault (no CLI login inside temp container at all).
* If CLI login is required (device code flow, etc.), run it in the temp container but:

  * Mount a dedicated ephemeral volume, extract only the minimal file(s), then wipe the volume.
  * Ensure terminal transcripts are **not** stored, or are redacted.
  * Never pass secrets through query strings or logs.

Also consider a Vault “delivery” mechanism rather than “inject at container start”:

* For long-running workspaces, you either (a) inject once and secrets linger on disk, or (b) fetch on-demand with short TTL.
* Vault’s agent/sidecar model is commonly used to render secrets into a filesystem view and renew them, which is the direction you want conceptually (even if you’re not on Kubernetes). ([HashiCorp Developer][2])

### 4) WebSocket auth + session binding

WebSockets often get less scrutiny than REST endpoints. You need:

* JWT validation on **every** WS upgrade.
* Explicit binding: `projectId` must be authorized for that user (not just “exists”).
* Rate limits / connection caps per user.
* WSS only (terminate TLS at a reverse proxy).

(There are real examples of WebSocket “container terminal” endpoints getting command injection / parameter injection bugs—treat the WS layer as high-risk.) ([GitHub][3])

This is an exceptionally well-structured and technically sound plan. You have clearly defined the boundaries of the system, chosen a modern but efficient stack, and addressed the core challenges of running headless agents (isolation and I/O).

Here is a review of your implementation plan, highlighting strengths, potential bottlenecks, and specific architectural refinements.

### 1. Architectural Strengths

* **Protocol Choice (`docker exec` vs SSH):** Your decision to use `docker exec` with PTY streams over the Docker Socket is the correct architectural choice. It eliminates the need to manage SSH keys, host keys, or run `sshd` inside the ephemeral agent containers. It keeps the containers "clean."
* **Isolation Strategy:** Giving each agent its own container and volume ensures that if an agent hallucinates and runs `rm -rf /`, it only destroys its own sandbox, not the host or other projects.
* **Monorepo Structure:** Using `pnpm workspaces` is perfect here. You will likely share Types (API interfaces) between the frontend and backend, and a monorepo makes that seamless.

### 2. Critical Deep Dives & Risks

#### A. The Credential "Dance" (Headless Auth)

**The Challenge:** You mentioned: *Temp container for auth → extract credentials*.
Most CLI tools (Claude Code, gcloud, etc.) trigger an OAuth flow that attempts to open a local browser (`localhost`). On a headless VPS, this will fail.
**Refinement:**

* You will need to run these CLIs with flags that force "no-browser" or "copy-paste" mode (e.g., `gcloud auth login --no-browser`).
* **The UI Flow:** The terminal needs to detect when the CLI is asking for an auth code. The user copies the URL from the web terminal, opens it on their local machine, authenticates, and pastes the resulting code back into the web terminal.
* **File Extraction:** Once auth is complete, you must know *exactly* where that specific tool writes its config (e.g., `~/.config/claude/config.json`). You can then read that file stream, encrypt it, and store it.

#### B. HashiCorp Vault vs. "Just Enough" Security

**The Challenge:** HashiCorp Vault is robust but heavy. It requires initialization, unsealing, and token management. For a single-user or small-team VPS, this might be over-engineering that introduces maintenance friction.
**Refinement:**

* **Alternative:** Consider using **AES-256-GCM** at the application layer. Store the encryption key in the Backend's environment variables (Docker secrets).
* **Why:** You are already trusting the host machine. If an attacker has root on the VPS to dump the SQLite DB, they likely have access to the Vault memory/container too. App-layer encryption simplifies the stack significantly (removes one container and complex service logic) while keeping the DB rows opaque.

#### C. WebSocket Stability & Resize Events

**The Challenge:** Terminal connections are fragile.
**Refinement:**

* **Heartbeats:** Ensure `lit-shell` and your backend implement a ping/pong heartbeat to prevent Nginx/Reverse Proxies from killing idle terminal connections.
* **Resizing:** The most common bug in web terminals is window resizing. When the frontend `lit-shell` component resizes, it *must* send the new rows/cols to the backend, which must call `stream.resize({ h, w })` on the docker execution stream. If you miss this, text wrapping will break inside the CLI, confusing the AI agent.

### 3. Tech Stack & Library Recommendations

* **Terminal:** If `lit-shell` is a wrapper around **xterm.js**, that is excellent. If it is a custom implementation, I highly recommend swapping to `xterm.js` with the `fit-addon` and `webgl-addon`. It is the industry standard for a reason (performance, ANSI handling).
* **Docker Interface:** `dockerode` is great, but ensure you handle stream demultiplexing correctly. `docker exec` sends stdout and stderr on different channels. You usually want to merge them for the PTY output.
* **File Watching:** For `x-files`, instead of polling, consider using `chokidar` (or similar) on the backend to watch the mounted volume. When the AI writes a file, the frontend should visually update immediately.

### 4. Refined Database Schema (SQLite)

Your schema is missing a crucial link: **Environment Variables**.
AI Agents often need more than just their auth token; they need `API_KEY`s for third-party tools.

```sql
CREATE TABLE project_env_vars (
  id INTEGER PRIMARY KEY,
  project_id INTEGER,
  key TEXT NOT NULL,
  value_encrypted TEXT NOT NULL, -- Encrypted at app layer
  FOREIGN KEY(project_id) REFERENCES projects(id)
);

```

### 5. Security Checklist (VPS Specific)

1. **Docker Socket:** You are mounting `/var/run/docker.sock` into your Backend container. This gives the backend root access to the host.
* *Mitigation:* This is acceptable for a control plane, but ensure the Backend container is not exposed directly to the public internet. Put it behind a reverse proxy (Nginx/Caddy) with Basic Auth or OIDC *before* the request hits your Node app.


2. **Container Limits:** Set CPU/Memory limits on the Project Containers. Coding agents can be resource-intensive; you don't want one agent crashing your control plane.
